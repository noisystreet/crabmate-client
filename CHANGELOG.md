# Changelog

User- and maintainer-facing changes for **crabmate-client** (official Client shells + business UI).

Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning is intended to follow [Semantic Versioning](https://semver.org/).  
Server-side changes (contracts / SSE / CORS, etc.) live in [CrabMate](https://github.com/noisystreet/CrabMate) and are not duplicated here.

On release: move `[Unreleased]` entries into a new version section and tag (e.g. `v0.1.1`). Write maintainer-readable summaries; do not list every internal commit.

## [Unreleased]

### Added

- **TUI: the default theme is now transparent — the palette hands both background slots back to the terminal.** The TUI resolves a semantic palette from the Desktop theme name; there was no way to ask for "let my terminal background show through", and the only transparency-adjacent knob was `/background` with an image, which answers a different question. A terminal cell has no alpha — its background is either some RGB or `Color::Reset` (meaning "paint nothing here, use whatever is behind") — so a transparent theme can only be all-or-nothing, never the `rgba(surface, .6)` a stylesheet can express. `shadcn-transparent` is therefore `shadcn-dark` with `bg` and `chrome_bg` set to `Reset`: the transcript and the chrome bars (session/workspace columns, status bar, composer) render on the terminal's own background, while `fg` / `muted` / `accent` / `hit` / `border` / `code_bg` / `selection_bg` / `overlay_bg` / `ok` / `err` keep the dark preset's real colours, so code blocks, selections and the settings card stay opaque and the layout reads through characters and borders instead of filled bands. It is the palette you get whenever **no** theme is set — including the window between startup and the serve prefs arriving — while an unknown theme name deliberately falls back to `default-dark` rather than to transparency: a front-end theme the TUI does not know yet should degrade to a readable solid UI instead of a silent blank one. `Palette::default()` is decoupled from that resolution on purpose and stays solid too, so test fixtures that assume filled bands keep working. An explicit serve-side theme still wins, and the new `default-dark` name keeps the previous solid dark look one switch away (`CM_TUI_THEME=default-dark`, or just pick any prefs theme). `CM_TUI_THEME` exists for exactly that local override, because theme names otherwise come from the serve prefs; it accepts only the listed presets (`crabmate-light` / `shadcn-light` / `shadcn-dark` / `material-dark` / `high-contrast-dark` / `shadcn-transparent` / `default-dark`) and ignores anything else, so a typo cannot silently collapse the UI to the fallback. Transparent slots survive the 16-colour downgrade untouched (only `Rgb` values are snapped), and `CM_TUI_COLOR=none` still outranks everything by switching to the fully mono palette. Tests: the preset resets exactly those two slots and nothing else, `from_theme(None)` and an empty string resolve to it while `Default` and any unknown name stay on `default-dark`, every listed name maps to its own palette, `CM_TUI_THEME` overrides the serve pref for known names and is ignored for unknown ones, `CM_TUI_COLOR=none` still outranks any theme choice, the downgrade keeps `Reset` slots, and a `TestBackend` render confirms the status bar and chat area come out `Reset` while the foreground and inline-code background stay solid. Cases that need two distinguishable solid fills now name `shadcn-dark` explicitly instead of leaning on `Palette::default()` — the fallback is no longer a solid palette, so that assumption had to go. Visually unverified: no real terminal here, and on a terminal that is not itself transparent the result is "the terminal's default background", not a wallpaper. No protocol change.

- **TUI: the pixel-graphics probe now recognises Konsole and Warp, and `/background` reports the probe snapshot when it refuses.** Both terminals implement the kitty graphics protocol and appear in kitty's own list of implementations, but neither set a `TERM_PROGRAM` value the probe knew: Konsole sets only `KONSOLE_VERSION`, and Warp sends `TERM_PROGRAM=WarpTerminal` while `TERM` stays a plain `xterm-256color`. A Konsole user therefore ran `/background` and got "current: halfblock" with no way to tell a probe gap from a terminal limit. `KONSOLE_VERSION` is now a kitty signal, `TERM_PROGRAM=WarpTerminal` joins the existing match, and `crabmate-tui caps` prints it alongside the other inputs. This tier can afford to be looser than Sixel: kitty graphics travel as `ESC _G` (APC), which terminals that do not implement it **ignore outright**, so a wrong guess costs a missing background instead of the screenful of garbage a false Sixel positive produces. Konsole's support is version-dependent (`22.04` brought Sixel; the graphics protocol came later), so older builds will simply show nothing — which the probe cannot distinguish from a draw failure. WezTerm is still deliberately *not* counted here, for the reason recorded in the `/background` entry below (per ratatui-image's QA matrix its kitty and sixel paths are buggy and only iTerm2 is clean). Separately, the refusal message used to name only the resulting pick, which forced a second window to run `caps`; it now carries a one-line snapshot (`TERM` / `TERM_PROGRAM` / `mux` / `protocols` → `picked`) plus the concrete next steps — which terminals work, and that tmux / screen need passthrough plus `CM_TUI_IMAGE=kitty`. Both `caps` and the hint render that snapshot through one `summary()`, so their wording cannot drift apart, and `caps` echoes the raw `CM_TUI_IMAGE` value itself, so `auto` or a typo no longer reads as `(unset)`. Three tests cover Konsole detected from `KONSOLE_VERSION` alone, Warp from `TERM_PROGRAM`, and the summary naming the multiplexer as why a terminal fell back to half-block. Still an environment-variable guess, not a capability query — see the "no active query" rationale in the entry below. No protocol change.

- **TUI: `/background <path>` paints a full-screen pixel background *under* the transcript by speaking the kitty graphics protocol directly.** The capability probe added last round answers "can this terminal draw pixels"; this is the first consumer, and it deliberately does **not** go through `ratatui-image`: that crate renders kitty images as unicode placeholders (one cell each) and never exposes the `z` parameter, so it can only *occupy* cells — it cannot sit *below* the text, which is the entire point of a background. Three facts from the protocol spec shape the implementation. First, `z` is a 32-bit z-index and only a negative value puts the image under the text, so every placement carries `z=-1`. Second, and this is the one that decides the architecture: **"When scrolling the screen… images must be scrolled along with text"** — the image moves with the transcript, while ratatui's diffed draw only knows about character cells and will happily paint over it; the background is therefore re-placed after *every* `draw()`, not once at load time. Third, `C=1` suppresses the cursor movement that placing an image otherwise performs, because ratatui owns the cursor position. Transmission uses `a=T,f=100` (PNG) with `q=2` so the terminal stays silent — any response would race the full-screen event loop for stdin. The image is decoded, capped to a 1920px longest edge, **dimmed to 35%** and re-encoded locally: the TUI layer has no translucent overlay to put between art and text, so readability has to be bought in the pixels, and a bright photo at full strength makes the `#eef1f6` body unreadable. Display size is *not* computed from cell pixel dimensions — `c=<cols>,r=<rows>` lets the terminal scale, which is why no `TIOCGWINSZ` probing was needed at all. Gating is strict: the pick must be `Kitty`, because sixel and iTerm2 have no "below the text" semantics, and the same probe already handles the terminal matrix (WezTerm included — it falls back to iTerm2 for the reason recorded last round). `Background` is off by default and only exists while a path is set; `/background` with no argument reports the current image, `off` / `none` / `clear` / `default` deletes it (reusing `clear_word`), `crabmate-tui caps` remains the way to inspect the probe. In `repl` the command is intercepted with an explicit "tui only" message rather than falling through as a chat message — `is_control_slash` has no wildcard, so without that entry `/background` would have been sent to the model as prose. Resize deletes the old placement and retransmits with a fresh image id (the old `c/r` span no longer holds), and exit deletes the image explicitly: leaving the alternate screen clears it anyway, but the terminal's per-buffer image quota should not depend on that. Covered by seven unit tests — chunk boundaries (non-final base64 chunks land on 4096 and stay 4-byte aligned), **the chunks concatenated back must decode to the exact original bytes** (the one that would catch any off-by-one in key/payload splitting), `z=-1`/`C=1` presence, dimming a real PNG on disk (255 → dimmed but non-zero, alpha preserved), and non-zero distinct image ids. **Not visually verified**: this repo's checks have no kitty terminal, so the byte-level protocol, resize path and cleanup are what is tested; the actual look needs a human in kitty or Ghostty. No protocol change.

- **TUI: `crabmate-tui caps` reports the terminal's pixel-graphics capability, and the colour-depth probe moved to one place.** The client had no way to answer "can this terminal draw a background image", and that answer decides which of four routes is even possible: Kitty graphics (true pixels, and the only one that can sit *under* text), Sixel and iTerm2 inline images (true pixels, but outside ratatui's `Buffer`, so a redraw erases them), and half-block characters (`▀`, pure ratatui, but sharing the cell with the text). The new `tui_mode/term_image.rs` classifies a terminal from environment variables alone — `TERM` / `TERM_PROGRAM` / `COLORTERM` / `LC_TERMINAL` / `KITTY_WINDOW_ID` / `TMUX` / `STY` / `NO_COLOR` — and `crabmate-tui caps` prints that snapshot alongside the resulting pick. There is deliberately **no active query** (DA1, `XTGETTCAP`, Kitty's `a=q`): answering one needs raw mode plus a timeout-bounded read, while stdin is already contended by the full-screen event loop and readline, so a badly sequenced read eats a keystroke or hangs startup. The classification is therefore a guess from the known support matrix, and it deliberately **under-reports** — a false Sixel positive leaves garbage on the screen, which is worse than no background image. Two consequences: inside tmux / screen the pixel protocols are *not* selected by default (whether passthrough is enabled cannot be confirmed), falling back to half-block with `CM_TUI_IMAGE=kitty` as the explicit override; and `NO_COLOR` / `TERM=dumb` disable image drawing outright, since every route except the text fallback needs colour, while half-block additionally requires 256 colours because 16 colours renders noise rather than a picture. `CM_TUI_IMAGE` (`none` / `halfblock` / `sixel` / `kitty` / `iterm2`) mirrors the existing `CM_TUI_COLOR`. The colour-depth decision was extracted here too: `Palette::resolve` kept its own `COLORTERM` / `TERM` truecolor test, and two copies would eventually disagree ("palette on truecolor, images on 16"), so both now call `term_image::color_depth`; palette behaviour is unchanged (only `TrueColor` keeps `Rgb`, 16- and 256-colour terminals both take the 16-colour downgrade, `NO_COLOR` / `dumb` still outranks everything). This is **capability only** — nothing renders images yet and markdown images keep degrading to `[图] alt`; the module exists so a later renderer has one source of truth instead of guessing again. Ten unit tests cover kitty, wezterm (which falls back to iTerm2, since its kitty and sixel paths are known-buggy per ratatui-image's published QA matrix), iTerm2, plain 256-colour, plain 16-colour (no image), `NO_COLOR` and `TERM=dumb`, the tmux back-off, `screen-256color` detection, every `CM_TUI_IMAGE` branch (including half-block on a 16-colour terminal degrading to none), and the `caps` output shape. No protocol change.

- **TUI: the full-screen client can resume an interrupted turn with `/resume`, which until now only `repl` could do.** The line-mode repl has recorded a dropped run's `x-stream-job-id` + `last_event_id` and re-attached with `stream_resume:{job_id,after_seq}` for a while; the full-screen `tui` had the same fields in hand (`ChatStreamOutcome` carries both) and simply never kept them — `ChatStreamArgs` was assembled with `stream_resume: None` in one place and nothing wrote a resume point, so a turn killed by a stalled connection, or by a Ctrl+C whose cancel request never reached `serve`, left the client with a job still running on the server and no way back to it. The full-screen client now keeps the same kind of point, under the same rule as `repl`: only when the server-side job may still be alive — a transport interruption (`TermError::InterruptedStream`, i.e. the job handle was already known), or `cancelled_by_user && !cancel_acknowledged`. A clean finish, an acknowledged cancel, or a run that never received a job id all clear it, because `/resume` on a finished turn would just make the model answer the same question twice. Two supporting changes were needed rather than one. First, the worker used to flatten every error into a `String` before handing it to the UI, which would have thrown away `job_id` / `after_seq` — the two numbers `/resume` actually needs — inside a human-readable sentence; `UiEvent::TurnDone` now carries an `interrupted: Option<StreamResume>` alongside the message, split off from `TermError::InterruptedStream` while the error is still structured, and the rendered text stays the only copy of the format string (`TermError`'s `Display`), so the two cannot drift. Second, `start_turn` was split into `build_turn_opts` (assemble `ChatStreamOptions` from override > user-data > serve defaults) and `dispatch_turn` (reset run state, remember the input, open the cancel channel), both moving to a new `tui_mode/turn_send.rs`; `/resume` calls the **same** assembly with only `stream_resume` filled in, so a resumed turn cannot quietly go out with a different model, temperature or role than the one that broke. Resuming deliberately does **not** re-print the user line — it is already in the transcript — and if the last row is still that turn's assistant block the reply simply continues into it (the common Ctrl+C case); when an error line sits in between, a `↻ 续传中断回合（job N，从 seq M 之后继续）` system row opens a new block instead of pretending the two halves are contiguous. The point is dropped on session switch and on `/conv new`, because it belongs to the transcript that broke and the client refuses to resume into a different conversation's history (it re-checks the conversation id and refuses if they disagree). Like the repl, the full-screen client does not auto-resume — its event loop has no retry loop, so the user decides. `tui_mode/resume.rs` holds the rule as a pure function (`resume_after_turn`) with six tests covering both keep paths and all four drop paths (clean finish, acknowledged cancel, no job id, no recorded message), plus `/resume` parsing (`/RESUME`, surrounding whitespace, and "resume the turn" staying a normal message) and the `/` menu entry — the menu's existing invariant test confirms every builtin candidate still round-trips through `parse_control`. No protocol change.

- **TUI: `/workspace` / `/cd` now expands `~`, and refuses the inputs it cannot resolve instead of handing them to serve.** The command posted its argument verbatim, so `/workspace ~/proj` sent a literal `~` to serve, which can only answer with a path-not-found error that says nothing about the real problem. Both `repl` and the full-screen `tui` now run the argument through a new `workspace_path` module first: `~` and `~/…` are expanded against the **local** `HOME` (`USERPROFILE` on Windows), and the expanded absolute path — not the typed string — is what gets POSTed and what the echoed line shows (`正在切换到工作区：/home/x/proj（按本机 HOME 展开 ~/proj）`). Nothing else is filtered: whether a directory outside the project pool is accepted is still a serve-side allowlist decision, so relative paths and every other shape pass through untouched. Two inputs are stopped on the client because the client can decide them without asking anyone: `~user` / `~user/…` (needs passwd / NSS, and guessing wrong lands in another user's home) and `~` when no home directory is readable at all (the expansion would silently become a relative path). Both print `切换工作区失败：…` and **send nothing**. A whitespace-only payload is refused for a subtler reason: serve reads an empty path as "restore the default root", which is not the switch the user asked for. `Path::join` dropping the base on an absolute argument is guarded too — `~//etc` resolves to `$HOME/etc`, not `/etc`. The clear words (`off` / `none` / `clear` / `default`) are checked before expansion and never reach it. They also close a long-standing gap on the `repl` side: its `/workspace` had no way at all to say "restore the default root", so `/workspace off` was posted as a directory literally named `off`; both entrances now share one predicate (`workspace_path::is_default_word`, which reuses `controls::clear_word` so the vocabulary cannot drift from `/model` / `/mode` / `/role`). One asymmetry is deliberate: the path belongs to the **serve host** (the Web input label says as much), so expanding on the client is only equivalent when TUI and serve share a machine; `CM_TUI_EXPAND_TILDE=off` passes `~` straight through for the remote case, where serve is the only party that can resolve it. The `/` menu entry and `/help` (`/workspace [path]`, `off`, `~/`) carry the matching hint. The Web path-input label deliberately does not: Web never expands, and whether serve does is not verified in this repo, so writing `~/` there would document an untested server behaviour instead of a client one. `ws_set_input` takes its resolver as a parameter so the reject paths are unit-testable without touching `$HOME`; tests cover `~` / `~/a/b` / trailing slash / `~//etc`, three `~user` shapes, the missing-home error (which must name the env-var escape), pass-through of absolute and relative input, the switch-off path, blank-payload rejection, and the "clear words never call the resolver" invariant. No protocol change.

### Changed

- **TUI: the top bar is now two segments — brand and workspace name — with the mode badge and key hints removed.** It used to be a single centred `Paragraph` holding only the workspace basename: half the row empty on each side, and nothing on screen said which mode (`ask` / `plan` / `act`) the session was in. A first attempt filled the right side with a mode badge (` ASK `) plus `Ctrl+E 思考 · F2 设置`, which turned out to be the wrong division of duties: the top bar answers "which workspace am I in", and putting session state and a permanent cheat sheet there made the row read like a manual instead of a location. The badge was the worse half — session mode already has a home in the status bar's `mode` segment, which carries a priority so a narrow terminal drops it before anything load-bearing, so duplicating it up top meant two things to keep in sync and two places to look. The key hints are learn-once information and do not deserve a permanently reserved strip. The bar therefore keeps `CrabMate` in `muted` on the left and the workspace name centred, and the session mode is the status bar's job alone. The centring is computed here rather than delegated to `Alignment::Center`: with a left segment present, centring the line as a whole makes the middle drift whenever the brand width changes. Each segment is measured with `UnicodeWidthStr` and the middle takes the remainder, padded on both sides, so the row's total width always equals the terminal width exactly (`Paragraph` neither wraps nor pads). Degradation is a single step now: below 13 columns the brand gives way (9 columns of brand plus the 4-column name floor) and the bar is what it always was, a centred name; the workspace name is the one thing that never goes away. The floor follows the name's own width rather than a fixed 4 columns, so a two-column workspace name with 11 columns to spend keeps the brand instead of dropping it to satisfy a minimum its name does not need. The bar lives in a new `tui_mode/topbar.rs` with its tests rather than growing `render.rs`, which sits at 823 of its 920-line budget. Covered by six unit tests (brand and name at 80 columns with an exact-width assertion and explicit negative assertions that `ACT` / `Ctrl+E` / `F2` never come back, a width invariant sampled at ten widths from 3 to 200, the 12-vs-13-column brand threshold, the short-name case keeping the brand, the 8-column fallback keeping only the centred name, and the placeholder when no workspace is known) plus one buffer-level assertion that the top row carries no `accent` background cell and still uses the strip colour — span-level tests alone only prove the style was *computed*, which is how inline-code backgrounds stayed invisible for a whole release. No protocol change.

- **TUI: the status bar's "generating" indicator is a six-cell instrument strip instead of a spinning Braille glyph.** The right edge used to read `⠋ 生成中`, one rotating character; it now draws six cells — `□` unlit, `■` lit — with a single square block walking left to right and wrapping around, a marquee rather than a bar. Both glyphs are the *same square* with and without fill, so all six lamp positions are always on screen and the moving one has a fixed frame of reference; and because the lit/unlit difference is carried by the glyph itself, the strip still reads when every palette slot collapses to `Reset` (`NO_COLOR`) or a colour degrades away on an 8-colour terminal. Exactly one cell is lit, never a run: a bar that fills up would be read as *progress*, which the client cannot know, while one lit cell of six reads as *motion*, which is all it can honestly claim. The frame number is the existing `StatusInfo.spinner` (advanced by wall clock every 120ms in `spinner.rs`), so no timer, no new state and no layout change was needed — the strip is built where the single glyph used to be. It halves that rate, flipping one cell per *two* ticks (240ms), by dividing the frame number inside the status line rather than by touching `SPINNER_INTERVAL`: that interval is shared with the folded-thinking row and the in-progress tool rows, whose Braille rotation is right at 120ms and should not slow down along with the status bar. The lit cell takes `accent` + bold and the rest take `muted` — deliberately *not* the darkest `border`: the unlit glyph is a thin outline, so the darkest slot erases it, and on an 8-colour terminal `border` snaps to black and matches `chrome_bg` exactly, which would remove the six lamp positions altogether. No new palette slot was needed (`accent` / `muted` + `BOLD` / `DIM` is enough). Width is fixed at 6 columns regardless of frame, so the wrapping budget and the right edge never jitter. The right edge occupies a fixed 8 columns in every state — idle (`○ 空闲`, 6 wide), generating (the 6-column bar), cancelling (`✳ 取消中`, 8 wide) — with content right-aligned inside it, and those 8 columns are what the budget subtracts: the left side (`serve` / `model` / `find`) therefore never shifts when a turn starts or ends. Previously the generating state claimed 13 columns (bar + `生成中`) against idle's 6, so every state change slid the entire left side sideways by seven columns. Generating carries no text at all: a scanning bar already says "running", and it is the two *static* states that need words. Degradations: `NO_COLOR` / `TERM=dumb` light the walking cell with `REVERSED` (a single cell, not the large-area reversal the project still avoids) and dim the rest — the `□` / `■` pair still separates the two by shape alone; under 8-colour downgrade `muted` keeps a visible grey, so all six positions stay on screen. A new `CM_TUI_REDUCED_MOTION` env var (read once per process via `OnceLock` — this sits on the render hot path) lights the whole bar steadily instead of scanning (a static *empty* strip would be indistinguishable from nothing, and there is no longer a `生成中` label to fall back on); the remaining motion effects from the direction draft are expected to share it. Idle (`○ 空闲`) and cancelling (`✳ 取消中`) are unchanged and stay static. `status_line_with` takes the flag as a parameter so tests never depend on the ambient environment. Tests: six new in `status`, asserting exactly one cell is lit and that it advances one cell per step, constant row width across frames, `REVERSED` under `mono`, both glyphs (`□` / `■`) being one column wide and equal in width, the right edge keeping a fixed 8 columns across all three states with the left side identical in each, and reduced motion lighting the whole bar; the three existing assertions that matched the rotation by *character* were rewritten to assert the constant shape and styling instead. No protocol change.

### Removed

- **TUI: the top bar is gone; the workspace name moved into the right column's title.** The one-row strip (brand on the left, centred workspace name) had already been narrowed down to a location indicator, and on a wide terminal the same name is printed in the workspace column's own header — so the strip spent a whole row repeating what the tree title already said, while the transcript lost a line to it. `tui_mode/topbar.rs` is deleted whole (193 lines plus its six unit tests), `Panes` loses `top`, the vertical split becomes `[Min(1), Length(1)]`, and the body now starts at row 0. Two consequences are stated plainly rather than papered over: the workspace name is only visible while the right column is (`SIDEBAR_MIN_WIDTH` = 120), so on a narrower terminal nothing on screen says which workspace is open; and the transcript's first line now sits flush against the top edge, where the strip used to be the one row of breathing space. The `top_bar_has_no_mode_badge_or_hints` buffer test goes with the bar (its assertion object no longer exists), while `every_theme_paints_bands_and_chat_area_from_palette_slots` moves its strip checks from row 0 to the status row and now asserts row 0 is chat background; `overlay_tests` / `render_tests` recompute the body rect (`H-2` → `H-1`, `1..` → `0..`) instead of hard-coding row numbers. Tests 524 → 517. Visually unverified. No protocol change.

### Fixed

- **TUI / Web: a code block could swallow the rest of a message — the shared normalizer was eating closing fences.** `normalize_markdown_for_render` ran every line through the same per-line rewrites with no idea whether it was inside a fence, and one of them (`normalize_trailing_orphan_fence`) strips a trailing ``` / ~~~ run from any line that does not itself start with a fence — meant for prose like `#### 标题``` `, where a stray opener would otherwise swallow the next paragraph. But models routinely glue the **closing** fence onto the last line of code (`fn main() {}``` `), and inside a block that same shape is the terminator: the normalizer deleted it, the fence never closed, and everything after it was drawn as code — in the TUI every remaining line took the `code_bg` background (`md::assistant_styled_text` keeps `in_fence` until a switch line appears, and a marker that no longer sits at line start is not a switch), in Web the rest of the message disappeared into `<pre>`. Reproduced before touching anything: with a fence opened by ` ```rust `, the code line `fn main() {}``` ` normalised to plain `fn main() {}` — the closer gone — leaving the trailing prose inside an unterminated block. The normalizer now tracks fence state itself, with the same predicate as the TUI renderer (`trim_start` + ` ``` ` / `~~~`, any indent) so the two cannot disagree about whether a line opens a block, and it updates that state on the **expanded** lines — one input line can become several (`依赖：```rust`, a merged table header). Inside a fence it does no per-line rewriting at all, which also fixes a quieter defect of the same origin: `###NotAHeading` and `-规范` inside code used to have a space injected, i.e. the client rewrote code it was only supposed to display. A trailing fence run inside a block is now split onto its own line instead of deleted, so the terminator actually terminates. Replay additionally runs the terminal-state guard `balance_unclosed_fence`: an odd number of switches means the last opener is an orphan (a model that stopped mid-marker, or a display-merged body whose seams do not pair up), and that one line is demoted to plain text so the remainder of the message stops being painted as code. Streaming deliberately does not use it — an unterminated fence mid-stream is the normal state, and "fixing" it would make the block jump the moment the terminator arrives. Five new tests: the glued closer, fence bodies left untouched, and the balance guard on odd input, on even input, and on the last (not first) opener. `normalize_strips_trailing_fence_on_heading_like_line` still holds, so the prose case the rule was written for is unchanged. No protocol change.

- **TUI: replay no longer shows the same reasoning twice, and a replayed answer is no longer built from a body that still carries the thinking.** `ReplayRow` emitted a `Thinking` row from the *raw* `reasoning_content` even when the message also carried `display_content`, while serve may already merge that same reasoning into the display body (Web hydration documents exactly this, with "勿再叠加") — so the thinking appeared once as a collapsed `Thinking` row and again at the head of the answer, and that seam is one of the ones that pushes the body's markdown off its structure (see the fence fix above). `display_reasoning` now resolves in three steps instead of two: `display_reasoning_content` wins outright (it and the raw field are two versions of one text); otherwise, if the raw reasoning is already contained in `display_content`, no separate `Thinking` row is emitted; otherwise the raw text still gets its own row. That last branch is a deliberate divergence from Web hydration, which drops the raw field whenever `display_content` exists — right when the server merged, but it silently loses the thinking when it did not, and the response alone cannot tell the two apart, so the substring check decides and falls back to keeping the content. Tests: doubling is suppressed when the body contains the reasoning, `display_reasoning_content` still wins over the raw field, and a message without `display_content` keeps its `Thinking` row as before; the existing `replays_roles_in_order` fixture (a body that does *not* contain the reasoning) still produces both rows. No protocol change.
- **TUI: replayed tool rows now read the same as the live transcript — real tool name, `✓`/`✗`, and the green/red body colour.** Two defects stacked up. First, `role=tool` messages carry a `tool_call_id` but not always a `name`, and the replay row fell back to that id, so reopening a session printed `[工具] call_abc123 (done) — …`; `conversation_messages.rs` now collects `tool_call_id → function.name` from the `assistant` messages' `tool_calls` (the only place the name is guaranteed to exist) and resolves tool rows through it, and when even that misses the row says `tool` rather than leaking an id that means nothing to a reader. Tests: two in `conversation_messages` (name resolved from the call site; an unknown id does not leak), three in `history` (envelope unwrapped via `summary`; missing `summary` falls back to the output head; `ok: false` reaches the row as `Some(false)` with a `✗`). ## [0.7.0-alpha.1] - 2026-10-19

### Added

- **TUI: typing `/` in the composer now opens a completion menu of builtin commands and skills, the way Desktop's composer does.** The full-screen TUI had the opposite problem to a missing feature: the commands existed, but nothing surfaced them — `/help` printed a wall of text *after* you already knew what to type, and skills were not reachable at all, since the skill list only ever arrived via `GET /skills` to the Web client. Now a draft that is `/` plus an optional prefix (no whitespace, no second `/`) opens a list above the composer: builtin commands first, then skills sorted by id. `↑` / `↓` step (wrapping), `Tab` / `Enter` accept, `Esc` closes until the draft leaves the prefix state — the same trigger rule and key map as Web, deliberately, so muscle memory crosses over. Accepting writes the command's full text (`/model ` keeps a trailing space to type arguments into; `/help` does not) and collapses the menu even though `/help` is still a bare prefix, which is why the "dismissed" flag exists rather than deriving openness from the draft alone. The candidate list is built in the TUI, **not** copied from Web: Web's menu carries `/agent`, `/export`, `/config`, `/api-key` and friends, none of which the TUI has a handler for, and offering them would mean handing the user a pick that either falls through to the model as a chat message or prints "unsupported". A test pins the invariant that every builtin candidate survives `parse_control`, so the menu can never list something the submit path would treat as prose. Skills come from `GET /skills` (the new shared `paths::SKILLS`; a `disabled` skills dir contributes nothing), fetched once when the menu first opens, cached — a failure is cached too, otherwise every keystroke inside the prefix state would retry the same broken request — and dropped on workspace switch, since the skill dirs are resolved per workspace. Rendering is a card at the bottom of the chat area (max 8 rows, window follows the cursor, two-column label + description) using `overlay_bg` with the selected row on `selection_bg`, the same slots the approval dialog uses. A footer line says *why* there are no skill candidates when the fetch failed or the skills dir is disabled — without it, "this workspace has no skills" and "the request broke" look identical — and it never eats the whole screen: at least one row of transcript survives even in a very short terminal. Typing anything else, or opening an approval prompt, does not fight it: the menu only consumes arrows/Tab/Enter/Esc, and it is not drawn at all while an approval is pending. Up/Down are only taken when there is something to move through, so `/zzz` (no candidates) keeps the old "arrows scroll the transcript" behaviour. The key → action map is a pure function (`slash_menu_action`) tested on its own, and `Tab` deliberately consumes the key even with no candidate while `Enter` yields to the send path. Covered by `slash_menu` tests (prefix rule, filtering, skill sort/cap/disable, empty-description falling back to the path, wrapping and clamping, dismiss semantics, the `parse_control` invariant, failed-fetch caching, the key map incl. Alt+Enter and the empty-candidate cases, and `TestBackend` assertions that the card reaches the buffer with the selected row on `selection_bg` and that the footer states the skills reason). No protocol change.

- **TUI: the sidebar session list can now delete sessions with `Delete` / `Shift+Del`, matching Desktop's two-step semantics.** The full-screen TUI could only *create* sidebar rows (`n`) or reclaim the disposable blank one it had just created; there was no way to get rid of an old conversation from the sidebar at all, while Desktop has had `Delete` (confirm, then delete) and `Shift+Delete` (delete immediately) as window-level hotkeys. `Delete` now arms a confirmation that is shown in the sidebar's own hint line (`[y] 删除 [Esc] 取消`) instead of an overlay — the hint line is already there, and a modal would have to take the keyboard away from the column you are deleting from; `y` / `Enter` confirms, `Esc` / `n` cancels, and any other key cancels and is then handled normally, so an arrow key both drops the pending delete and moves the cursor. `Shift+Delete` skips the confirmation. Behind them is a new `SessionIndexOp::Delete`, which deliberately is **not** `RemoveBlank`: that one is the sideways bookkeeping done when you switch away from a session you never used, so it refuses rows with content, drafts, pins or stars, whereas this one deletes what the user explicitly picked, messages included. Two rules mirror Web: the deleted row's `active_session_id` must land on a row that still exists (the caller's `next_active` is re-validated against the freshly fetched array and degrades to the first surviving row), and deleting the last row leaves one default blank session behind (`ensure_at_least_one`) so the index never becomes empty and `active` always has a target. Guards: the session a turn is currently streaming into cannot be deleted (its SSE tail still has to write the reply back — Desktop blocks the same way), deleting the current session clears the local `conversation_id` and transcript so the next message cannot be sent into it, and the `/conv new` bookkeeping (pending row id / bind / title / selection) is dropped when that row is the one deleted. Deleting the *current* session then lands somewhere instead of leaving the TUI with nothing to talk into: the neighbouring row (below first, else above) when it carries a `server_conversation_id`, otherwise a fresh session via `/conv new`'s reuse-or-create path. That landing is required rather than cosmetic — `bind_new_session` only ever writes a `server_conversation_id` back to a row created by `/conv new`, so a conversation started immediately after the delete would otherwise live on the Server while the sidebar and every other client never learned about it. A delete whose target vanished underneath the confirmation now says so and refreshes the column instead of silently doing nothing. And if the history replay for that landing fails while there is no previous conversation to fall back to — exactly the state the delete leaves behind — the TUI starts a new session instead of sitting there bound to nothing, since replay failure used to restore the old binding and, with no old binding, that meant no row to bind the next turn to: the same hole the landing exists to close. The persisted conversation is deleted too, best-effort and silently, via `DELETE /conversation/{id}` — deleting only the sidebar row would leave an orphan the client can never reach again, which is exactly what Desktop avoids — and it rides *inside* the same index op, issued only after the `PUT` succeeded: the opposite order would leave a sidebar row whose conversation is already gone (an entry that opens empty) whenever the index write failed. Pending deletion is discarded whenever focus leaves the column (Tab / `w` / a click elsewhere / F2 / an approval overlay), so a stale confirmation cannot fire later. The key → action mapping and the neighbour choice are pure functions with unit tests (`sidebar_action`, `adjacent_session`), since "does `y` really delete" and "where does the cursor land" are the parts that are worst to verify by hand in a terminal. The hint text was re-fitted to the 26-column sidebar (`Del删`, `n新`, `r刷`) and both sidebar hints are now width-checked by the existing test. No protocol change.

### Changed

- **TUI: the bottom status bar is gone on wide terminals — status now lives in a vertical stack at the bottom of the right column, matching Desktop's layout.** Desktop moved its status elements out of a bottom bar into a collapsible vertical stack docked at the bottom of the right workspace column (`.side-status-stack`, `flex-direction: column`) some rounds ago; the full-screen TUI kept a single full-width row. Two reasons that row had to go. It cost a whole transcript line on every terminal, and the row was a *horizontal* one: the right column is 26 columns wide, so a horizontal strip in that space truncates almost immediately (`serve http://… │ model … │ role …` does not fit three items), while a vertical stack gives each segment its own line and therefore its full value. So on wide terminals (`sidebar_visible`) `layout::panes` no longer carves out a bottom row at all — `Panes.status` is `None` — and the right column is split `[tree Min(1), stack N]` instead, which hands that row back to the transcript. The stack itself is a new module (`status_stack`): one line per segment (`serve` / `model` / `role` / `mode`, plus `find` and `↑N` when active) with the run indicator right-aligned on the **last** line — Desktop's `.side-status-stack` puts chips first and the run indicator after them, which in a column means bottom. Right-aligned is the same bearing the horizontal bar had (its run indicator was pinned to the right edge), only the reference is now the column width instead of the row width, so the indicator sits at the bottom-right corner rather than the bottom-left. That order also keeps the stack still: the bottom row is the one that changes, so starting or finishing a turn does not shift the segments above it. Each value is truncated to the column with `truncate_display` so a long base URL cannot spill. The conversation id is **no longer shown** — Desktop's status area has no such chip either, and a truncated id on its own line carries no information the left column's `*` marker does not already give; the old `conv` segment is gone together with the `conv` parameter it was threaded through `status_line` / `stack_lines` (a left-over parameter would just invite someone to re-add the line). `MAX_STACK_ROWS = 8` caps it (a quarter of a 24-row terminal is already a lot to give up) and segments beyond the budget are dropped by the same `Segment::priority` the horizontal bar uses — the budget changed from columns to rows, the ordering did not. Two invariants are stated in code rather than left implicit: `status_stack::stack_rows` and `status_stack::stack_lines` are the same source (count ≠ rendered lines shows up as a blank row at the bottom of the stack or a clipped last segment), and `draw` and `on_mouse` share one `TuiApp::status_stack_rows` (two computations drifting shows up as "clicking the right column moved the wrong row" — an unattributable symptom). `F3` toggles the stack to a single run-indicator line, the terminal equivalent of Desktop's collapsed stack. **Narrow terminals (<120 columns) keep the bottom bar**: both columns are hidden there, so there is nowhere to put the stack, and the bar carries states that must always be visible (generating / cancelling / approval blocking) — Desktop has a rail mini-dot and a mobile top-bar dot as fallbacks, the TUI has no equivalent, so deleting the bar would not be symmetry but a regression. One structural note: `F3` went in via a new `on_hotkey` that also took over the existing `F2` check, because `on_key`'s if-chain already sits at the lizard CCN≤10 gate (`toggle_thinking_with_notice` was extracted for the same reason); moving `F2` in is a net-zero change in branches, which is what made room for `F3`. Four new layout tests (no bottom bar + stack sits flush at the bottom + tree and stack abut; narrow keeps the bar; stack rows clamped so the tree keeps a row; zero stack rows leaves the tree full height) and five in `status_stack` (collapsed is one line; expanded is one segment per line in display order; `stack_rows` equals the rendered line count; long values truncate to the column; the row budget is capped). Verified: `crabmate-tui` 529 tests, `clippy --all-targets -D warnings`, `fmt --check`, `fn-nloc-ratchet` 916/199, `lizard` max CCN 10. **Visually unverified** — this is a layout-rect change and no real terminal was used, so spacing, the seam between tree and stack, and whether 8 rows is the right cap all still need a human look. No protocol change.

What was missing was any place that said so: `/help` in both front ends listed only `/quit`, and the repl banner read `Ctrl+C / Ctrl+D / /quit`, so a user who reached for the more common `/exit` had no way to tell whether it worked or whether it had just been sent to the model as a chat message. The TUI help line now reads `/quit（/exit、/q 同义）`, the repl help line and banner list `/exit`, and the parsers' tests assert the aliases explicitly (`/exit`, `/EXIT`, ` /Exit  `, `/q` for the TUI; `/quit`, `/exit`, `/EXIT`, `/q` for the repl) instead of only `quit`. Behaviour is unchanged — in particular `/exit` while a turn is streaming still cancels the turn first and exits once it unwinds, exactly like `/quit`. No protocol change.
- **TUI: wrapped lines keep their block's shape.** Two separate defects, both visible as "the block gets chewed off at the edge". **Code blocks:** a line longer than `code_width` was split by the generic wrapper, and only the first segment had been padded to the block width — the tail segment ended short, so the right edge of the `code_bg` rectangle lost a notch wherever an over-long line appeared. Code lines are now split up front with every segment padded to `code_width`. **Lists, tasks, headings and quotes:** continuations started at column 0, so a wrapped bullet looked like a new paragraph and a wrapped quote visually broke its own vertical rule at the line break. This has to happen while the character stream is being built, not in `wrap_styled_chars` — the wrapper only sees a flat stream and cannot tell which block a line belongs to. Passing `0` as the width still opts out, leaving the body unwrapped. Covered by six `md_tests` (quote bars on every row, nested bars preserved, list / task / heading / ordered-item hanging indents) plus a rewritten over-long-code-line test asserting every segment is full width. - **TUI: inline images degrade to `[ 图 ] alt` instead of leaving a stray `!`.** The shared inline parser has no `Image` variant, so `![alt](url)` used to split into a literal `!` (plain text) plus an ordinary link — the transcript showed a lone exclamation mark followed by underlined text, which reads like a rendering bug. The TUI now scans for `![alt](url)` itself and emits an `accent` `[ 图 ]` tag plus the alt text (which keeps its own inline styling; an empty alt leaves just the tag). The URL is not rendered, only validated — incomplete syntax such as `![x](` or `![x]` is left untouched so a broken fragment is not swallowed, and fences keep `![x](u)` literal since that is code. ### Fixed

- **TUI: replaying a session no longer renders the tail of an assistant message as a code block.** Loading a session could paint the rest of a reply inside a `code_bg` rectangle, verbatim — markdown markers and all — because the replay-side fence balancer and the renderer disagreed about *which lines are fence rows*. `balance_unclosed_fence` ran on the **raw** message text, while rendering first passes the same text through `normalize_markdown_for_render`, and that normalizer splits an opener glued onto prose (`依赖：```rust`) into its own line. So the two sides counted different row sets: with one glued opener plus one ordinary code block the raw count came out odd, the greedy pairing found the *closing* fence unpaired, and the balancer blanked it — manufacturing exactly the unterminated fence it exists to prevent. Everything after that line (in that message) was then drawn as code, which is why the text looked like raw markdown rather than a rendering bug. It is the same defect class the previous fence fix addressed, one layer up: that change taught the normalizer to split glued openers but left the balancer counting an older row set, so the two changes cancelled out and the balancer could actively corrupt input that had been correct. The fix makes the row set single-sourced: `normalize_markdown_for_render_checked` returns `(String, FenceState)` from the **same** pass that expands the lines, `normalize_markdown_for_render` stays a thin wrapper over it (behaviour unchanged, both call sites untouched), and `balance_unclosed_fence` now normalizes first and only then demotes the last unpaired opener (`demote_last_opener`) when the state came back `Open`. The diagnostic is deliberately separate from the disposition: streaming must **not** demote, because an unterminated fence mid-stream is the normal state and "fixing" it would make the block jump the moment the terminator arrives — so the state is reported and the caller decides, instead of the balancer guessing on the caller's behalf. Five new tests in `markdown_normalize`: a glued opener plus a normal block reports `Balanced`; a real orphan opener reports `Open` with its body intact; `balance_unclosed_fence` keeps two blocks closed in that same glued shape (this is the one that fails on the old implementation); and normalizing its own output is idempotent across four shapes, which matters because replay normalizes once and the renderer does it again. Verified: `crabmate-client-api` 130, `crabmate-tui` 523, `frontend` markdown 98 all pass; `clippy --all-targets -D warnings` and `fmt --check` clean; `fn-nloc-ratchet` 916/199. No protocol change.

- **TUI: inline code in assistant messages now actually gets its background.** `md_row_style` carried only `fg` and the modifier bits when merging a markdown span onto the line's base style, so the `bg(code_bg)` that `md_span_style` computes for `` `inline code` `` was thrown away before rendering — the span style was correct, the pixels were not, and `md_span_style`'s unit tests only proved the former. `md_row_style` now carries `bg` too (falling back to the base style's `bg`, which stays `None` for transcript rows so nothing else changes). - **Status bar: the context chip now reads the model window's true fill level, and its displayed value never decreases.** The chip was labelled *Context* and showed `used / max_input`, where `used` (server `used_input_tokens`) carries a per-turn fixed cost — the tool schemas plus the vendor overhead, ≈37k at the 160k window — so the numerator included a constant the denominator did not, understating the ratio and making a 45% fill read as ~26%. ### Changed

- **TUI: blank lines between paragraphs in an assistant reply are now rendered, matching Desktop.** The chat column's markdown pipeline (`tui_mode/md.rs`) dropped every blank line before wrapping: `wrap_styled_chars` only pushed a row when the current row had content, so `甲\n\n乙` came out as two adjacent lines while the same text in Desktop produced two `<p>` separated by `.msg-md-prose p { margin: 0.5em 0 }`. Nothing upstream was at fault — `normalize_markdown_for_render` (shared with Desktop) and `assistant_styled_text` both preserved the blank line; it died in the last step. `wrap_styled_chars` now pushes a row on every `\n`, so an empty row survives as one blank terminal line, and `assistant_styled_text` gains the CommonMark semantics Desktop gets from `pulldown-cmark`: a run of blank lines at a paragraph boundary collapses to exactly one (several blanks are still a single paragraph break, never multi-line whitespace), leading and trailing blank lines add no gap, and blank lines inside a fenced code block are preserved verbatim (Desktop's `<pre>` keeps them too), including when the stream stops inside a still-unclosed fence — the trailing-blank trim only runs once the fence has closed, since trimming there would make the line vanish mid-stream and reappear when the block closes. `wrap_physical` — the plain-text path used by tool output and the composer — is deliberately unchanged, so non-markdown rows keep their old tight packing. List semantics stay approximate: Desktop's CommonMark wraps a *loose* list item's content in `<p>` (an extra margin), while the TUI only inserts one blank line, so the spacing is equivalent but the list structure is not re-laid-out. Five `md_tests` cases pin the shapes and two `render_tests` cases pin that the gap survives into `BodyRow` (a md-level test alone cannot notice a renderer that filters empty `Line`s — which is what the original bug was). There were previously no blank-line assertions at all, which is why the divergence went unnoticed. No protocol change.

- **Shared client logic: the session data model and its rules moved into `crabmate-client-api::session_model`, so Desktop and TUI no longer keep separate copies of "is this a blank session / may this row be reclaimed / reuse-or-create an empty session".** `ChatSession`, `StoredMessage`, `StoredMessageState` and the seven layout / id constants moved out of `frontend/src/storage.rs`, together with `session_is_blank_chat` / `session_is_unbound_empty_chat` / `prefer_or_create_empty_session` (from `session_workspace_partition.rs`) and `is_disposable_blank_session` / `reclaim_disposable_blank_session` (from `session_ops.rs`). These are **client-local** types — the Server stores that array as opaque JSON — so they are not contract types and stay outside `contract_pin.md`. The shared module stays pure: the two DOM touchpoints (`js_sys::Date::now()` / `Math::random()`) became injected parameters (`new_session_id(now_ms, entropy)`, `new_empty_session(..., now_ms, ...)`), which also unifies the row-id format both ends already used (`s_<ms>_<entropy>`). `frontend/src/storage.rs` now re-exports the shared types, so the existing `crate::storage::X` references across 59 files compile unchanged, and behaviour is identical (a whitespace-only `server_conversation_id` still counts as unbound; reusing a blank row with no `workspace_root` still keeps that row's existing binding). Motivation: the TUI's `/conv new` had re-implemented these rules against `serde_json::Value`, and the two copies drifted once already — TUI treated a missing title as the default, while Web's `is_default_session_title("")` returns `false`. The TUI now reads the same types: its session-index row checks deserialize the row into `ChatSession` and call the shared predicates, while **writing still goes through the original JSON** — a row is never rebuilt from the thin projection, so other clients' `messages` survive — and a row that fails to deserialize is never treated as blank, so a malformed row cannot be reused or reclaimed. The title rules moved too: `is_default_session_title` now lives in the shared crate, and `title_from_user_prompt` takes the caller's localized default (Web passes `New chat`, the TUI passes `新会话`). No protocol change.

- **TUI: `/conv new` now registers the session in the shared session index, so it actually shows up in the left rail (and in Web / Desktop).** The rail renders `GET /user-data/workspaces/current/sessions` — an index the Web client maintains with a full-list `PUT` — while the TUI only ever read it, and `/conv new` merely cleared the in-memory `conversation_id`; so a new session never appeared, neither immediately (there was no row) nor after the first turn (the Server persisted the conversation, but no index row pointed at it). `/conv new` now runs a `GET` → reuse-or-insert a blank row → `PUT` cycle on that same index: when the index holds no blank session, a row titled *新会话* is inserted first and becomes `active_session_id`, and the rail shows it on the refresh that follows, moving the cursor to that row **by id** (the array order is the Server's storage order, so "first row" is not assumed); either way the row carries the empty-`messages` shape the Web side parses. Pressing `/conv new` again while that write is still in flight is ignored rather than inserting a second blank row, and if the row has meanwhile been deleted by another client the failed bind drops the pending reference, so the next `/conv new` inserts a fresh row instead of retrying the same dead id forever. Picking that still-blank row in the rail and pressing Enter now answers *这就是当前新会话（还没有 server conversation_id）：直接输入即可* instead of going through a switch to a conversation that does not exist on the Server yet (which would also have dropped the pending bind). When the first turn returns a `conversation_id`, it is written back into that row as `server_conversation_id` — the field the rail's `>` marker, `/conv use <id>` and a Web-side reload all key on. Repeat `/conv new` without sending a message reuses that still-blank row instead of inserting another, and the reuse test is the Web's own: the `GET` result is scanned for a blank session (`messages` empty, no `server_conversation_id`) exactly like `prefer_or_create_empty_session`, so an empty row created by Web / Desktop is adopted rather than duplicated. Leaving such a row without sending anything now drops it again, mirroring `reclaim_disposable_blank_session`: the delete only fires for *disposable* rows (blank, no draft, not pinned / starred) and, when the row is `active`, only together with the row id of the session being switched to — otherwise the Server would be left with `active_session_id` pointing at a deleted row, and in that case the row is kept. The same reclaim runs when the `NewBlank` write lands after the user already switched away: the unclaimed row is dropped instead of lingering in the rail. A `conversation_id` that arrives while the `NewBlank` write is still in flight is no longer lost — it is held and bound as soon as the row id is known, matching the Web client, which writes the id onto the turn's bound session rather than into whatever session happens to be active. The row's *name* follows the Web rules as well, not just its storage: it starts at the Web default title (*新会话* — `i18n::default_session_title(ZhHans)`, since the TUI's own strings are Chinese-only; a Web client on another locale re-renders that same default into its own language), and the first message sent renames it exactly like the Web composer does — newlines flattened, whitespace runs collapsed, and anything past 48 characters cut to 47 plus `…` (`title_from_user_prompt`). The rename carries the same guard: it only fires while the title is still a default one, so a session already named elsewhere keeps its name and a whitespace-only message leaves the default in place. The code comment claiming the Web side never renames on the first message was simply wrong; the TUI now matches it instead of leaving every session at *新会话* forever. Because the Server stores this array **verbatim** (each row is the Web client's full `ChatSession`, `messages` included), the write starts from the raw JSON the `GET` returned and touches only the target row — rebuilding the array from the TUI's thin projection would have wiped other clients' session bodies. Write failures are reported as a system line and leave the TUI conversation usable, just unregistered. Residual risk worth knowing: these are read-modify-writes against a list the Web client also writes on a debounce, so two near-simultaneous edits can race and last-write-wins. No protocol change.

- **TUI: transcript blocks are now divided by a hairline rule instead of a blank line.** Blocks in the full-screen `tui` transcript (user / thinking / assistant / tool / system) used to be separated by one empty row; that row now carries an extremely dim, full-width `─` rule in `palette.border`, indented to the previous block's message-prefix width so it begins where that block's text begins. - **TUI: the status bar's *generating* indicator is now an animated spinner.** While a turn is in flight the right-hand slot used to read a static `● 生成中`; it now cycles a 10-frame Braille spinner (`⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏`) at one frame per 120 ms. The event loop already redraws unconditionally every frame (2 ms when events arrive, 50 ms otherwise), so no timer and no extra throttling were needed — but the frame is advanced by wall-clock time rather than once per redraw, because a per-redraw step would run the spinner ~25× faster while a reply streams in. The idle (`○ 空闲`) and cancelling (`✳ 取消中`) states stay static, and the frame index resets when a turn ends so the next turn starts from the first frame; the glyphs are plain characters, so `NO_COLOR` terminals keep the animation. The state lives in a new `tui_mode/spinner.rs`, since the event-loop module was already at its line-count limit. The same spinner also replaces the `▸` marker of a collapsed *thinking* row while that row is the last one in the transcript and the turn is still generating (historical folded thinking rows keep the static marker, and the Ctrl+E expanded view is untouched); because the transcript — unlike the status bar — is rebuilt only when an invalidation key changes, the animated mark is substituted at render time rather than entering that key: the buffer is re-tokenized and re-wrapped only when the content really changes, so a model pause no longer costs a full transcript rebuild every 120 ms. No protocol change.

- **TUI: an in-flight tool row now carries a progress slot that spins while the tool runs.** A tool row was silent between its start frame and its result — it showed only the tool name — so a 30-second `exec` looked exactly like one that had hung. Rows without a result (`tool_ok == None`) now carry a `⠿` progress slot after the `[工具] ` prefix, and the renderer swaps that slot for the same 10-frame Braille spinner the status bar uses whenever the row is the last line of the transcript and the turn is still generating; as soon as the result lands the slot is gone (finished rows already carry `✓ / ✗` from `tool_end_text`, so nothing is doubled up). The slot is a static placeholder inside the memoized body rows and is substituted at render time — exactly like the folded-thinking mark — so a tool that runs for minutes does not force a full transcript rebuild per frame, and since the slot and every spinner frame are one column plus a space, wrapping never shifts. The inter-block hairline's continuation indent now comes from the previous row's actual prefix width (an in-flight tool prefix is two columns wider than a finished one), so rules stay aligned with the text they follow. No protocol change.

- **Chat: *regenerate* after *stop generation* now defers to the Server's authoritative branch instead of truncating locally.** Regenerating a user message dispatches on `(conversation_id, revision, user ordinal)`: with all three known it takes **PATH A** (`POST /chat/branch`, the Server truncates and re-runs), otherwise it fell back to **PATH B** — a purely local truncation that re-sends the same user text over the existing stream. After a *stop generation* the revision is unknown (it is only ever learned from a `conversation_saved` frame, which the abort path never receives because the client aborts the stream right after POSTing `…/cancel`), and the Server now **persists** the interrupted turn, so PATH B's local truncation would have diverged from the Server store and duplicated the still-present user message. A new middle branch (**PATH A′**) closes that gap: when the conversation id is known but the revision is not, the client first calls `GET /conversation/messages` to read the Server's current `revision` (which already includes the persisted interrupted turn), writes it back through `session_sync` (`apply_saved_revision_if_same_conversation`), and only then takes PATH A — so PATH B is now reached only when the id or the ordinal is genuinely unknown. No protocol change.

No protocol / pref-key change.

The toolbar button in the workspace column head (`StatusBarToggleBtn`), its `status_bar_visible` signal, and the pref (the `/user-data/prefs` field plus the Android-enter default that hid the bar on mobile) are all removed; the `status_stack_collapsed` header row still folds the body, so the old "reclaim vertical space" need is served by collapsing rather than hiding. See `docs/design/context_usage_visualization.md` §3.

The two `assistant_answer_phase` sources (the outer loop and the SSE parser) are wire-identical, so the frame cannot be told apart on a shared channel — the reasoning needs its own routing. The Web client now registers the dedicated `on_reasoning_delta` hook the TUI already used: `ChatStreamCallbacks` gains `on_reasoning_delta`, `delta_apply.rs` adds `apply_chat_stream_reasoning_delta` / `chat_stream_on_reasoning_delta_builder` (writes the chunk to the tail's `reasoning_text`, lane-independent), and `sse_frame.rs` wires `SseControlSink::on_reasoning_delta` to it instead of leaving it `None`; the shared parser / sink comments record that the `None` fallback to `on_delta` is only a safety net. Covered by the new Playwright case `e2e/specs/mock-post-tool-thinking.spec.ts` and two routing unit tests in `sse_frame.rs`.
- **Chat (Web): a thinking bubble produced before a tool call no longer drifts below that tool call once the turn finalises.** While streaming, the pre-tool reasoning was written into the current loading tail bubble's `StreamTextOverlay.reasoning`; on `TOOL_CALL_START` the tail is pinned below the freshly inserted tool row (and later rotated / finalised), so the thinking, carried along with the tail, moved from above the tool to below it — the commentary lane already had a `turn-commentary-{tool_call_id}` anchor, the reasoning lane had none. The reasoning is now lifted off the tail at the tool boundary and anchored into a dedicated `turn-think-{tool_call_id}` assistant row placed in front of the same tool (behind the same-key commentary row when one exists, matching the streaming order): `on_tool_call_declared` reads the tail's overlay reasoning (`stream_overlay_reasoning_for_message`) before inserting the tool, calls the new `TurnRowQueue::upsert_reasoning_before_tool` (which reuses the commentary anchoring and archive helpers, and a shared `new_assistant_projection_row` constructor so a reasoning row is a commentary row with a reason instead of a text), and then clears that reasoning off the tail (`stream_overlay_clear_reasoning_for_message`) so the later pin / rotate cannot bring it back below the tool. The `turn-think-` prefix joins `has_v2_finalized_rows`, so a session holding a reasoning row is recognised as a v2 projection and merged append-only rather than wholesale replaced. Covered by the new Playwright case `e2e/specs/mock-thinking-bubble-drift.spec.ts`.

The token now resolves at `:root`, and both overlays add their own `padding-bottom` from it (the settings page already scrolls, so it becomes scroll headroom; the modal's `.modal` cap gains `100%` so a tall dialog still fits the padded backdrop) — zero without a keyboard, so the existing layout is unchanged. The default theme is `shadcn-light` (near-white `--surface`) while the shell's `windowLightStatusBar` / `windowLightNavigationBar` are pinned to `false` (white icons, designed for a dark bar), so a white icon sat on a near-white band and was invisible. The two flags cannot be switched from the resource layer (the mirror gate freezes them to `false`), so the fix tracks the theme at runtime: `theme_css_is_light()` in `frontend/src/app_prefs.rs` classifies a CSS slug by its `-light` suffix, and `persist_theme_to_storage_and_dom()` — the single `data-theme` write point, covering prefs load, the settings preview and the OS dark-mode listener — calls the new `apply_mobile_system_bar_icons` JS bridge right after writing the attribute; that reaches `CrabMateMobile.setSystemBarIconAppearance`, and `MainActivity.applySystemBarIconAppearance()` drives `WindowInsetsControllerCompat.isAppearanceLightStatusBars` / `isAppearanceLightNavigationBars` (light theme → dark icons). - **Chat (Web / Desktop): dismissing the queued-message chip no longer drops the typed text, and the find bar navigates with Enter / Shift+Enter.** Two follow-ups from the 2026-09-13 chat review. The stream-time queue chip's `×` used to set `ComposerStreamFollowUp::Idle` and discard the queued body outright; it now parks the text through the existing `queued_draft_to_park` + `flush_composer_draft_to_session` path — writing it back into the queued session's stored draft (`frontend/src/app/chat/column.rs`) and, when that session is still the active one, refilling the composer input so the text is visible again immediately (the `+` new-session path already did the parking half). Separately, the in-chat find bar could only step between matches through the ↑ / ↓ buttons; its input now maps Enter to the next match and Shift+Enter to the previous, mirroring the IDE find bar (`prevent_default`, so the `type="search"` field carries no other side effect).

- **IDE: the tab strip no longer rebuilds the following tabs (and loses keyboard focus) when a tab is closed or pinned.** The strip was a keyed `<For>` whose key was `format!("{idx}:{path}:{pinned}")` — it baked the tab's *position* (and its pinned flag) into the identity. Closing a tab shifts every later tab's index down and pinning one reorders the list (`reorder_tabs_pinned_first`), so the key of each subsequent tab changed, `keyed` tore down and rebuilt those DOM nodes, and the focused tab lost focus. The same snapshot also leaked into the accessibility plumbing: `prop:id` and `data-testid` were captured at creation as `ide-tab-{index}`, so after a close or pin they pointed at the wrong row while the arrow-key handler still looked up `get_element_by_id("ide-tab-{next}")` by the *live* index. The strip now uses `<ForEnumerate key=|tab| tab.path.clone()>`, keyed on the stable, unique file path, and passes its live `ReadSignal<usize>` index into the row: closing or pinning only moves the DOM nodes, `children` does not re-run, and the row derives its active state, dirty mark, `prop:id` / `data-testid` (folded into one `Memo<String>` that tracks the live index) and every click / context-menu handler from that index, so the id the arrow keys resolve is always the row they mean. Because a moved-but-unchanged row keeps its DOM, the value-captured `pinned` and the dirty mark would have gone stale, so `pinned` is now resolved live from the tab list by `path` (`tab_is_pinned`), and `tab_display_dirty` / `active_editor_is_dirty` read the tab list and editor signals *tracked*, so the reused `<Show>` / `aria-label` refresh on signal change (the async, read-only callers have no reactive owner, so tracking is a no-op there).
- **TUI: transcript blocks (user / thinking / answer / tool / system) are now separated by a blank line, matching the Desktop column.** The full-screen renderer's only spacer rule was "blank line when two *message bubbles* are adjacent", so a thinking block flowed straight into the answer and a tool row straight into the following text — a turn read as one dense wall, while the Web / Desktop chat column separates every block with `.chat-tui-transcript { gap: var(--space-5) }` around one `<section class="chat-tui-turn">` per block (thinking, answer, tool process). `render::build_body_rows` now treats a `LineKind` change as a block boundary and inserts one blank row there, so thinking / answer / tool / system each get their own block while same-kind neighbours stay compact (consecutive tool rows, matching Desktop's single `chat-tui-tool-process` block). The spacers live only in the render product — `UiState::lines` is untouched, so `search_total`, the in-place `tool_pending` result update and `view_offset` row accounting do not shift. `BodyRow.log_index` becomes `Option<usize>`: a spacer belongs to no logical line (`None`), so the `/find` anchor (`rows.iter().position(...)`) cannot stop on a blank row — it previously carried the *next* line's index, which anchored one row early. No protocol change.
- **TUI: colors now follow the Desktop theme, and the transcript says what it means with color instead of one hard-coded palette.** Six `const Color` values (blue status bar plus `Indexed` sidebar / chat / composer / top bar) and the `kind_style()` foregrounds (`LightCyan` / `LightGreen` / `LightMagenta` / `LightYellow`) were fixed at compile time: the TUI never read `UserPrefsDto.theme` (the field has been deserialized in `serve/user_data.rs` all along) and nothing kept contrast on a light background — the `/find` anchor row was `fg(Black) + bg(Yellow)`, which smears on a white surface. A new `tui_mode/palette.rs` maps the five Desktop presets (`crabmate-light`, `shadcn-dark`, `shadcn-light`, `material-dark`, `high-contrast-dark`; values copied from `frontend/themes/*.css`) onto a semantic `Palette` (`fg` / `muted` / `accent` / `hit` / `bg` / `chrome_bg` / `border` / `code_bg` / `ok` / `err` / `mono`), with the `tokens.css` root values as the default for a missing or unknown theme; light presets take `--surface-hover` as the chat background so the screen is not pure white. The theme is applied once, after the startup `GET /user-data/prefs` (`PersistedSettings.theme` → `UiState::set_palette`), so switching it requires a restart and the settings panel gains no writable field. Terminal capability is handled by `Palette::resolve`: `CM_TUI_COLOR` (`none` / `basic` / `truecolor`) overrides first, then `NO_COLOR` / `TERM=dumb` drop to a colourless palette where semantics ride on `DIM` / `BOLD` / `REVERSED`, and otherwise a `COLORTERM` / `TERM` truecolor probe decides whether each `Rgb` stays or is snapped to the nearest of the 16 ANSI colours (values with visible chroma only compare against chromatic candidates, so an accent is not pulled onto grey). On the semantics side: message prefixes are `muted` + `DIM` (system warnings stay `err` + `BOLD`), collapsed thinking rows carry a `▸` marker, inline code moves from `fg(Cyan)` to `bg(code_bg)` + body colour and links from `fg(Blue)` to `accent`, tool rows colour by outcome (success `ok`, failure `err` + `BOLD`, in-flight `muted`; `LogLine` gains a render-only `tool_ok`, the text contract is unchanged), and search hits get their own `hit` slot (anchor row `bg(hit) + fg(bg)`, other matches `fg(hit)`) so they no longer collide with the user bubble's `accent`. Overlay backgrounds also move off the fixed `Indexed(236/234)` onto `chrome_bg`, which would otherwise be a dark box with dark text under a light theme. No protocol change.

- **TUI: the composer now has a border, a focus state and a placeholder.** The input area was a bare painted strip: the only affordance was whether the hardware cursor happened to be visible, so an empty composer looked the same as a disabled one. It now draws a `Block::bordered()` around the input — the border is `accent` while the composer actually owns the keyboard (`cursor_allowed && focus == Focus::Input`) and `muted` when focus sits in the sidebar / workspace tree or a modal holds the keyboard — and an empty buffer shows a `DIM` muted placeholder (`输入消息 · Alt+Enter 换行 · /help 查看命令`) that is painted, never inserted into the buffer, so typing the first character makes it vanish. Geometry follows the border: `composer_outer_rows` adds the two border rows to the `Layout` budget (and the composer height is clamped to `area.height - 1`, so the transcript keeps at least one row), while the content width and the cursor column are derived from `Block::inner` instead of the old hard-coded "indent one column" — which would otherwise have shifted the caret by a cell and clipped the last column. Terminals too small for a border (`width < 4` or `height < 3`) fall back to the old borderless drawing instead of producing a zero-width interior. No protocol change.

### Fixed

- **TUI: the transcript now keeps a one-column gutter on *both* sides of the chat column, instead of hugging the right edge.** `render_body` indented the text area by one column on the left and then let it run to the column's last cell (`area.width − 1`), and `chat_body_width` budgeted `column width − 1` to match — so wrapped rows stopped exactly on the chat column's right edge while the sidebar panes (`width − 2`) and the bordered composer both keep a column on each side. On a wide terminal the longest row butted into the workspace tree; on a narrow one it sat on the terminal's last column. The budget is now `column width − 2` and the text area is `area.width − 2` — the two must stay equal, since a budget wider than the drawn area re-introduces the clipped-tail bug above (a `Paragraph` with no `Wrap` cannot re-flow what it drops). `rendered_chat_area_keeps_right_gutter` renders one frame through a `TestBackend` and asserts both padding columns stay blank; `chat_body_width_matches_layout` pins the new arithmetic. Costs one usable column. No protocol change.

- **TUI: transcript rows no longer lose their last character(s) at the right edge — the wrap budget is computed in display columns, not character count.** Every logical row is pre-wrapped to `chat width − message prefix` so it never needs runtime wrapping, but the prefix width was taken as `prefix.chars().count()`. The prefixes contain CJK (`[你] ` / `[助手] ` / `[思考] ` / `[工具] ⠿ `), so 4–7 characters actually occupy 5–9 columns: the content budget was 1–2 columns too wide, `Paragraph` (no `Wrap`) then clipped the tail at the area's right edge, and because the wrap point had already been consumed the characters were not re-flowed onto the next row — the block looked like it overran the column instead of wrapping. A new `prefix_width` (`UnicodeWidthStr::width`) feeds both the content budget and the separator indent, so first physical rows now stop exactly at the chat column's right edge. Two regression tests guard it: `body_rows_never_exceed_width` (no built row is wider than the requested width, across row kinds and widths) and `rendered_chat_area_keeps_all_characters` (a 38-hanzi body renders through a `TestBackend` frame with all 38 characters on screen — under the old arithmetic the 38th was dropped). No protocol change.

- **Chat (Web / Desktop): `stream_ended.reason="truncated"` now renders its localized label instead of being echoed as an unknown reason.** The Server added the `truncated` terminal reason (upstream `finish_reason == "length"`, or a stream cut before `[DONE]`), but the front-end is still pinned to crates.io `crabmate 0.6.0`, whose `StreamEndReason` has no such variant — so `parse::<StreamEndReason>()` failed and the empty-reply diagnostic line fell back to echoing the raw string. `frontend/src/i18n/stream.rs` gains a small forward-compat table (`future_stream_end_reason_label`) plus `stream_end_reason_label_from_raw`, which tries the pinned enum first, then the table (`truncated` → 输出被截断 / `truncated`), then echoes the raw value; `stream_empty_reply_diag_line` now calls it. The done-bubble decision and the diagnostic-instead-of-summary behaviour are unchanged — only the label is localized. The table becomes dead code once the contract pin is bumped to a Server release that carries `StreamEndReason::Truncated`.

- **Chat (Web / Desktop): a turn that ended with visible output no longer shows the "(no reply: answer phase not entered)" placeholder just because its trailing bubble was deduped away.** When a turn streams text and then declares a tool call, the client's `demote_answer_before_tools` moves that text out of the answer lane into the pre-tool commentary lane and clears the answer-delta counter, so the terminal summary reaches `on_done` with `answer_phase = false` and `delta_chars = 0` — identical to a turn that produced nothing. In that state the loading tail is first emptied (`text.clear()`) and then removed by the final-answer / commentary dedupe, so `apply_stream_done_to_loading_assistant` missed its `assistant_message_id` and took the "missing tail" branch, which pushed the empty-reply diagnostic unconditionally — contradicting the Server, whose `StreamEndReason::Completed` is only ever emitted when the turn *does* have visible output (`Answer` or `ToolCalls`). The missing-tail branch now goes through `finalize_missing_loading_assistant`, which pushes the diagnostic only when the current turn (everything after the last `user` row) still has no user-visible output — a tool row, or a non-empty assistant row that is not filtered from the chat column (`is_empty_assistant_body` / `is_ephemeral_timeline_assistant_for_chat_ui`). A turn that produced only tool cards, or only commentary-plus-tools, is therefore left alone instead of being labelled "no reply". No protocol change.
